# Перекрытие упаковки и CUDA enqueue

FHERMA_ASYNC_INPUT: сначала полностью упаковывается первая пара A/B.
Перед отправкой готовой пары pool начинает следующую задачу. Caller выполняет
свою часть копирования, затем вызывает CUDA enqueue, пока остальные потоки
заканчивают упаковку следующей пары. После enqueue caller ждёт все worker
acknowledgments, и только затем публикует следующую задачу.

У каждой пары собственный диапазон pinned-буфера. Уже отправленные данные
не изменяются до завершения DMA. Если enqueue бросает исключение, выполняется
finish_inputs до выхода; затем fherma_run синхронизирует CUDA streams.
Входы можно освобождать после возврата/исключения. Init не имеет доступа к ним.

Проверки: 36 immediate/deferred transfer случаев, четыре искусственных
исключения с немедленным повторным использованием pool; варианты condition
variable и spin/ack. После разделения begin/finish также проходят 1050
последовательных copy/prefault задач. Все операции выполняются в run.

# Эксперименты с выходным вектором

FHERMA_OUTPUT_APPEND использует обычные reserve и insert: каждый готовый
фрагмент конструируется непосредственно из pinned-результата без resize
с предварительным заполнением нулями. Копирование в этом варианте однопоточное.

FHERMA_OUTPUT_SPARE сохраняет только один новый нулевой std::vector.
В каждом run его владение передаётся текущему Outputs, а новый нулевой вектор
выделяется и полностью инициализируется в этом же измеряемом run. В первом
вызове оплачиваются обе аллокации. Это проверка влияния CPU cache coherence:
работники копируют в область, которую caller не обнулял только что.
Нет хранения входов или результатов, повторного использования возвращённого
вектора, конечного пула выходов, перехватов allocator или изменения harness.
Каждый последующий вызов также оплачивает одну свежую аллокацию и обнуление.

Ни один из этих режимов не считается улучшением до GPU-измерения.


## Наследование CPU affinity служебными потоками CUDA

Диагностика 19426d2 обнаружила cuda-EvtHandlr на CPU0 вместе с caller.
895950b откладывает pin caller до конца init; рабочие потоки копирования
по-прежнему индивидуально закрепляются сразу. Создаваемые CUDA helpers
наследуют исходную разрешённую маску NUMA-узла GPU. Чужие потоки/процессы
не переназначаются, за пределы разрешённых CPU вариант не выходит.
Тест Linux проверяет наследование маски и финальную привязку caller;
локально дополнительно прошли 1050 copy/prefault jobs. Эффект измеряется.


## Полностью рабочие потоки на вводе

FHERMA_INPUT_WORKERS_ONLY добавляет шестнадцатого worker для упаковки,
освобождая caller для CUDA API. Всего 17 потоков вместе с caller;
на выводе caller по-прежнему копирует свою часть, дополнительный worker
не пишет результат. Число acknowledgments/CV pending учитывает новый
worker. Асинхронный pipeline теперь может перекрыть всю упаковку следующей
части с постановкой предыдущей, без отложенного memcpy на caller.
Проверены spin и CV: по 1050 jobs и 36 pipeline cases + 4 исключения.
ThreadSanitizer на асинхронном пути прошёл. Арифметика остаётся прежней.

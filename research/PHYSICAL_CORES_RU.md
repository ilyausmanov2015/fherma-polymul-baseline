# Размещение CPU workers по физическим ядрам

Диагностика ef3a49e, run 6aac3085b615118421bfaac8, показала:
24 разрешённых CPU — это 12 физических ядер с SMT-парами 0-1, 2-3, …,
22-23. Все относятся к package 0. Старый порядок 0,1,…,15 использовал
восемь ядер; worker на CPU1 разделял ядро с caller CPU0 даже во время
последовательного resize выходного std::vector.

FHERMA_PHYSICAL_CORES сначала выбирает по одному разрешённому CPU
с остальных физических ядер, затем их дополнительные SMT threads,
а sibling caller оставляет последним. Число потоков не меняется само:
16 и 12 проверяются отдельно. С 12 потоками размещение 0,2,4,…,22
использует по одному потоку на ядро; с 16 дополнительные CPU 3,5,7,9
не делят ядро с caller. Output workers получают первые отдельные ядра.

Выбор ограничен уже разрешённой GPU-local NUMA маской. Чужие потоки
не переназначаются. При отсутствии топологии каждый CPU считается
отдельным ядром, что сохраняет прежний порядок. CPU0 не зашит в алгоритме:
проверены все 24 возможных caller, sparse cpuset, несколько package
с повторяющимися core_id и отсутствующие sysfs-данные.

Проверки: чистый планировщик CPU и 1050 copy/prefault jobs локально;
Linux CI проверяет реальное применение affinity и CUDA-сборку. Изменение
затрагивает только размещение worker, арифметика прежняя fused radix-8.
Цель — проверить объяснение host overhead; численное ускорение ещё
не предполагается до GPU измерения.

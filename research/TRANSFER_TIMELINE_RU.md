# Передача данных и задержки конвейера

Цель: отделить копирование CPU↔GPU от преобразования входа и накладных
расходов. Ранее измеренные 176–178 мкс mapped prepare и 101–106 мкс вывода
не являются чистым временем PCIe и не задают аппаратную нижнюю границу.

## Методика

Два диагностических коммита на одинаковой арифметике fe5fc67:

- `7ed9670`: GPU читает mapped WC input, как в лучшем решении.
- `b78df3c`: H2D в отдельном CUDA stream, prepare читает device memory.

CUDA events отмечают начало/конец каждой части H2D, prepare и D2H,
а также границы NTT/CRT. CPU steady_clock отмечает готовность входной
части, окончание её постановки в очередь, ожидание выхода и его копирование.
CPU и GPU имеют разные начала отсчёта: их абсолютные отметки не вычитаются
и не совмещаются без дополнительной калибровки.

После получения обычного корректного результата в свежем std::vector
выполняются дополнительные DMA-пробы на принадлежащих реализации staging
и device buffers. Результат к этому моменту завершён; пробы его не изменяют.
Нет сохранённых ответов, переноса полезной работы в init или работы после run.
Поэтому полное время диагностического run непригодно для leaderboard.

Внутри каждого вызова два повторения:

- H2D 7 340 032 байта целиком и четырьмя частями.
- D2H 3 670 016 байт целиком и восемью частями.
- Для D2H: CPU прочитал pinned buffer перед передачей (`cached=1`),
  либо после предшествующей DMA CPU его ещё не читал (`cached=0`).
  Это описание действий, а не гарантия абсолютного состояния всех кэшей.
- Для восьми частей дополнительно включаются fenced completion writes;
  затем — чтение готовых частей CPU одновременно с дальнейшей DMA.

`gpu_us` включает исполнение команд между CUDA events, `host_us` —
вызовы API и ожидание завершения. Даже изолированная DMA-проба не измеряет
время только электрической передачи по линии. Пробы идут после арифметики,
поэтому отличаются от рабочего конвейера нагрузкой на GPU/CPU и состоянием
памяти. Дополнительные events и API-вызовы также меняют конвейер.

Разрывы между DMA-интервалами — измеренный промежуток между событиями,
в который могут входить уведомления и планирование. Без аппаратной трассы
его нельзя целиком назвать простоем GPU.

## Воспроизведение анализа

```sh
python tools/analyze_transfer_profile.py local/run-ID.json \
  --output results/transfer-ID.json
```

Первые два вызова пропускаются как прогревы. Для каждой DMA-конфигурации
сначала берётся медиана двух повторений внутри вызова, затем медиана полностью
сохранённых измеряемых вызовов. Этапы рабочего конвейера агрегируются отдельно.
Сырые отметки сохраняются в JSON для проверки расчётов. В этих двух запусках
API обрезал build_log до последних 12 000 символов: полностью остались вызовы
4 и 5. Расчёты используют только их, обрезанный вызов 3 исключён.

## Результаты 17 сентября, 23:35 МСК

Оба диагностических запуска прошли 3/3 и два прогрева:

- Mapped: `6aac4da6e3bdd1a55314d483`, полный диагностический run 3,396 мс.
- Staged: `6aac4e85b615118421bfbaa3`, полный диагностический run 3,446 мс.

Это время с шестнадцатью дополнительными DMA-пробами после завершения
полезного результата; оно не сравнивается с обычными 378 мкс. CPU-отметка
готовности результата до проб — около 424 мкс в обоих вариантах, также
с накладными расходами подробной инструментализации. CUDA CI обоих успешен.

уже показал отсутствие выигрыша: staged 381,7705 против mapped 378,0135 мкс.

Минимальные в этих пробах эффективные времена соответствуют приблизительно
53 ГБ/с на вход и 54–56 ГБ/с на выход. Сумма благоприятных изолированных
H2D+D2H — около 203–205 мкс, существенно ниже прежних «270–280 мкс».
Это достижимые результаты микропроб, а не новая аппаратная нижняя граница
и не обещание аналогичного суммарного score.

Разница после CPU-чтения воспроизвелась в обеих сборках и согласуется
с влиянием когерентности кэшей/размещения данных. Проба прогревает буфер
одним общим вызовом CPU-копирования; рабочий путь читает восемь частей.
Поэтому нельзя переносить штраф 65–72 мкс из пробы непосредственно на
рабочий путь или утверждать, что устранение этого штрафа даст столько же
ускорения score. В рабочем пути CPU-копирование выхода заняло 82–89 мкс,
ожидание готовности частей — всего 1–1,4 мкс: CPU и передача перекрываются,
и ускорение одной DMA может скрыться за CPU-работой.

Следующий проверяемый вариант `4239f41`: четыре принадлежащих решению
pinned-буфера для выхода вместо одного. В init выделяются только пустые
буферы; в каждом run очередной полностью перезаписывается новым результатом,
который копируется в свежий обычный std::vector. Ответы не переиспользуются.
Все профилировочные флаги выключены. GMP N32768: 9/9, включая два оборота
по буферам и случайный вход после граничных случаев.

Полный benchmark `6aac4f68e3bdd1a553150abb`: **20/20, 364,925 мкс**,
диапазон 352,917–380,700, среднее 364,90785 мкс. CUDA CI 35271837280
успешен. Это на 3,46% быстрее прежних конкурсных 378,0135 мкс и на 2,71%
быстрее контрольного benchmark 375,0745 мкс. Дополнительная pinned memory — 10,5 МиБ;
повторное использование четырёх буферов проверено на 22 вызовах с прогревами.

Конкурсный запуск `6aac5047b615118421bfbb96` подтвердил улучшение:
**20/20, 362,920 мкс**, диапазон 354,171–374,724, среднее 364,3478 мкс.
Это −15,0935 мкс / −3,99% относительно прежнего официального результата.
Leaderboard обновился: 3/6; первые два результата 259,8035 и 300,9985 мкс.
Новый вариант остаётся в main и прикреплён к FHERMA точным коммитом
`4239f41c068034f1689ae0cd4f5393737827a68c`; диагностические флаги выключены.

Измерение доказало наличие резерва в организации передачи и CPU-памяти,
но ускорение всего решения составило около 4%, а не разницу между двумя
изолированными D2H-пробами. Дальнейшие изменения нужно оценивать по всему
run: с копированием входа, формированием выходного vector и перекрытием
CPU/GPU, а не только по скорости одного cudaMemcpyAsync.
